# S5.5e Guest 冷启动与内存优化

## 阶段拆分

- S5.5e.1：增加默认关闭的 Guest boot trace，完成普通 cold 的 Host/Guest 时间对齐、
  `initcall_debug` 定向归因和 20 Pod 稳态内存基线。
- S5.5e.2：先消除 Guest 内核冷启动的确定性热点，目标为串行
  `PodScheduled→Ready P95≤1.5s`，且不删除 Kubernetes 已验收能力。
- S5.5e.3：裁剪不参与 Pod 运行的调试/硬件能力，目标为 20 Pod Pod-leaf
  `memory.current` 均值 `≤100MiB`，并完成能力回归。

S5.5d.3b 的 VMM/网络并行按用户决定延后；只有 Guest 优化后并发门禁仍受该顺序阻塞时
才恢复。

## S5.5e.1 结论

状态：`DONE`。同一 reviewer 终审 `PASS S5.5e.1`，P0/P1/P2=`0/0/0`。

普通 cold 的主要瓶颈已精确定位在 Guest 内核，不在 Agent：5 次串行样本中，Guest
`ttRPC server ready` 的 Guest monotonic P50/P95 为 `929/931ms`；Agent 自身从进程入口到
ttrpc ready 仅 `3～4ms`。Host `start_vm→vsock ready` P50/P95 为
`1138.668/1149.218ms`，`managed-start` P50/P95 为 `1167.865/1172.404ms`。

完整串口显示 `raid6_select_algo` 启动自测单次消耗 `476000us`。当前内核保留
`CONFIG_RAID6_PQ=y` 的同时错误启用了 `CONFIG_RAID6_PQ_BENCHMARK=y`；因此下一步只关闭
benchmark，继续保留 Btrfs/RAID6 能力。`initcall_debug` 还观察到 ACPI `68ms`、packet
scheduler `36ms`、OOM init `28ms`、cryptd `20ms`、conntrack `18.784ms`；这些结果受
`initcall_debug` 大量同步日志影响，只用于排序，不混入正式时延样本。

20 Pod 稳态下，每个 worker PSS mean/P50/P95 为
`101218.2/101367/101391KiB`，每个 Shim PSS mean/P50/P95 为
`5329.1/4955/6871KiB`；二者是可加总的进程账本，合计均值约 `104.05MiB/Pod`。
Pod leaf `memory.current` mean/P50/P95 为
`110027980.8/109744128/111726592 bytes`，即均值约 `104.93MiB/Pod`。该 cgroup 账本
不能再与 PSS 相加。

Guest 配置 512MiB RAM；容器内读取到 `MemTotal=471372KiB`、
`MemAvailable=430388KiB`。worker 的 `Pss_Anon` 约 `100.3MiB`，其中大部分是 Guest
内核保留页和工作集；`AnonHugePages` 常见 `94MiB` 左右。内核启动报告
`59256KiB reserved`，并含 `20480KiB code + 16136KiB rodata + 6428KiB init`，说明后续
内存优化应优先缩减 Guest 内核常驻 code/rodata 和 tracing 元数据，而不是回退
`cube-vmm-worker` 边界。

## S5.5e.3 Guest 常驻内存优化

状态：`DONE`。实现、云端性能/内存/能力/回退验收已完成；同一 reviewer 先给出
`PASS S5.5e.3 source/config early review`，最终终审为 `PASS S5.5e.3`，两次
P0/P1/P2 均为 `0/0/0`。

### 根因与实现

20 Pod 基线中 worker 的匿名大页约为 `94MiB/Pod`，而 Guest 内核 ELF 的运行时 `.BTF`
段约为 `5.95MiB`。该调试类型信息会随每台 VM 作为 Guest 内核常驻匿名页重复计费，但普通
Pod 启动和已验收的 BPF/JIT、kprobe/uprobe、ftrace、perf、livepatch 能力并不要求 Guest
暴露 `/sys/kernel/btf/vmlinux`。因此 PVM Guest 配置仅关闭
`CONFIG_DEBUG_INFO_BTF`/`CONFIG_DEBUG_INFO_BTF_MODULES`；保留 DWARF 构建信息、BPF/JIT、
kallsyms、kprobe/uprobe、function/dynamic ftrace、perf、livepatch、Btrfs、RAID6 和 dummy
netdev。通用 `kernel-oc9.x86_64.config` 原本就没有运行时 BTF，不需要重复修改。

同时为两个受支持的 Guest 配置启用 `MEMORY_BALLOON`、`BALLOON_COMPACTION`、
`PAGE_REPORTING` 和 `VIRTIO_BALLOON`。CubeShim 默认向 `cube-vmm-worker` 传递 size=0、
`deflate_on_oom=false`、`free_page_reporting=true` 的 balloon 配置，使 Guest 能把已释放页面
归还 Host；设置 containerd 与 watchdog 的环境变量 `CUBE_FREE_PAGE_REPORTING=0` 可完整移除
该 PCI/virtio 设备，恢复旧拓扑。worker 的 JSON IPC 对 `Some(balloon)` 与 `None` 都有往返
测试，普通创建和 snapshot restore 使用同一 `VmConfig`。Hypervisor 现有 balloon 实现同时
实现 `Pausable`、`Snapshottable`、`Transportable` 和 `Migratable`；本阶段不改变 S6 才验收的
Kubernetes PodSnapshot/Pause 产品协议。

候选 Shim/worker SHA-256 分别为 `2bc3a8dd…a63f5` / `83551ee5…056f64`；候选 Guest
kernel 为 `3ccea53f…3572a`，构建配置为 `90939ef1…`。仓库 `pvm_guest` 输入
SHA-256=`7c7f713e…ab2ce`，经 `make olddefconfig` 后与候选构建配置逐字节一致。候选 kernel
为 `48,143,360 bytes`，相对未裁剪构建的 `52,337,808 bytes` 减少 `4,194,448 bytes`；
历史构建 kernel `633bb982…dc0f` 与已验收回滚 kernel `24ff4d86…50a28` 均未覆盖。

### 稳态与压力结果

free-page reporting 单独开启但 Guest 从未分配大量匿名内存时，三轮 20 Pod 的
`memory.current` 均值仍为 `102.960/102.957/102.959MiB`，说明它不能回收从未借给 Guest
allocator 的启动常驻页。该失败实验保留，最终稳态收益来自 BTF 常驻段裁剪；balloon 用于
工作负载释放页的动态归还，而不是把二者混为同一个数字。

最终 BTF-off + free-page reporting 的 20 Pod 三轮结果如下：

| 轮次 | Pod leaf `memory.current` mean | P95 |
|---|---:|---:|
| 1 | 94.857MiB | 96.586MiB |
| 2 | 94.859MiB | 96.590MiB |
| 3 | 94.860MiB | 96.590MiB |

worker PSS 约 `88.976MiB/Pod`，Shim PSS 为 `4.822～4.826MiB/Pod`，worker
`AnonHugePages` 为 `84MiB/Pod`。相对 S5.5e.1 Pod-leaf 基线 `104.93MiB/Pod`，均值下降
约 `10.07MiB/Pod`（`9.6%`），三轮均满足 `≤100MiB/Pod` 门禁。

128MiB 两轮 Guest 工作集压力测试均完成 `ALLOC→FREE→ALLOC→FREE`。Host worker PSS 从
最低 `118.056MiB` 升至最高 `370.056MiB`，释放后尾值回到 `120.056MiB`；Pod cgroup 从
最低 `104.949MiB` 升至最高 `357.730MiB` 后回落。这证明内存可再次 fault-in，并在 Guest
释放后回到接近预压力水平。早期 220MiB 夹具触发 256MiB 工作负载限制 OOM、以及把 Perl
分配留在同一进程后误判释放的两次结果都标为夹具失败，不混入验收数据。
