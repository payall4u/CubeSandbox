# S5.5e Guest 冷启动与内存优化

## 阶段拆分

- S5.5e.1：增加默认关闭的 Guest boot trace，完成普通 cold 的 Host/Guest 时间对齐、
  `initcall_debug` 定向归因和 20 Pod 稳态内存基线。
- S5.5e.2：先消除 Guest 内核冷启动的确定性热点，目标为串行
  `PodScheduled→Ready P95≤1.5s`，且不删除 Kubernetes 已验收能力。
- S5.5e.3：裁剪不参与 Pod 运行的调试/硬件能力，目标为 20 Pod Pod-leaf
  `memory.current` 均值 `≤100MiB`，并完成能力回归。

S5.5d.3b 的 VMM/网络并行按用户决定延后；只有 Guest 优化后并发门禁仍受该顺序阻塞时
才恢复。

## S5.5e.1 结论

状态：`DONE`。同一 reviewer 终审 `PASS S5.5e.1`，P0/P1/P2=`0/0/0`。

普通 cold 的主要瓶颈已精确定位在 Guest 内核，不在 Agent：5 次串行样本中，Guest
`ttRPC server ready` 的 Guest monotonic P50/P95 为 `929/931ms`；Agent 自身从进程入口到
ttrpc ready 仅 `3～4ms`。Host `start_vm→vsock ready` P50/P95 为
`1138.668/1149.218ms`，`managed-start` P50/P95 为 `1167.865/1172.404ms`。

完整串口显示 `raid6_select_algo` 启动自测单次消耗 `476000us`。当前内核保留
`CONFIG_RAID6_PQ=y` 的同时错误启用了 `CONFIG_RAID6_PQ_BENCHMARK=y`；因此下一步只关闭
benchmark，继续保留 Btrfs/RAID6 能力。`initcall_debug` 还观察到 ACPI `68ms`、packet
scheduler `36ms`、OOM init `28ms`、cryptd `20ms`、conntrack `18.784ms`；这些结果受
`initcall_debug` 大量同步日志影响，只用于排序，不混入正式时延样本。

20 Pod 稳态下，每个 worker PSS mean/P50/P95 为
`101218.2/101367/101391KiB`，每个 Shim PSS mean/P50/P95 为
`5329.1/4955/6871KiB`；二者是可加总的进程账本，合计均值约 `104.05MiB/Pod`。
Pod leaf `memory.current` mean/P50/P95 为
`110027980.8/109744128/111726592 bytes`，即均值约 `104.93MiB/Pod`。该 cgroup 账本
不能再与 PSS 相加。

Guest 配置 512MiB RAM；容器内读取到 `MemTotal=471372KiB`、
`MemAvailable=430388KiB`。worker 的 `Pss_Anon` 约 `100.3MiB`，其中大部分是 Guest
内核保留页和工作集；`AnonHugePages` 常见 `94MiB` 左右。内核启动报告
`59256KiB reserved`，并含 `20480KiB code + 16136KiB rodata + 6428KiB init`，说明后续
内存优化应优先缩减 Guest 内核常驻 code/rodata 和 tracing 元数据，而不是回退
`cube-vmm-worker` 边界。

## 诊断实现边界

- 仅当 containerd 环境变量精确为 `CUBE_GUEST_BOOT_TRACE=1` 时启用；默认行为不变。
- 每个合法 sandbox ID 使用固定目录下独立的 `<id>.serial.log` 与
  `<id>.console.log`，拒绝路径穿越输入，并发不共享文件。
- 修复 `VmConfig::to_vm_config()` 无条件把 caller 的 serial/console 重置为 TTY 的问题；
  worker IPC 继续传递完整 `VmConfig`，因此 embedded/worker 语义一致。
- 本地 `cargo fmt --check`、定向 3/3 test、`cargo check` 和 `git diff --check` 均通过；
  云端 release build 通过。诊断 Shim/worker SHA-256 分别为
  `72ae612c…8d666` / `617d5592…59fa0`。

## S5.5e.2 Guest 内核确定性热点优化

状态：`DONE`。同一 reviewer 第三轮终审 `PASS S5.5e.2`，P0/P1/P2=`0/0/0`。

三个受支持的 Guest 配置统一保留 `CONFIG_RAID6_PQ=y`，仅关闭
`CONFIG_RAID6_PQ_BENCHMARK`。这不会移除 RAID6/Btrfs，只跳过每次 Guest 冷启动时按固定
顺序跑完全部 RAID6 实现的选型基准；内核仍根据 CPU feature 直接选择已注册的最高优先级
实现。候选 PVM Guest kernel SHA-256 为 `24ff4d86…50a28`，构建配置 SHA-256 为
`95e9d932…e025d`，仓库 `pvm_guest` 输入 SHA-256 为 `88340cb1…ace9`；同时保留
`CONFIG_DUMMY=y`、`CONFIG_BTRFS_FS=y` 和 `CONFIG_RAID6_PQ=y`。历史构建输出
`633bb982…dc0f` 未被覆盖。

5 次同条件预验收全部 Ready。Guest agent start 从 S5.5e.1 的 `916～927ms` 降为
`447～452ms`，ttrpc ready 从 `919～931ms` 降为 `451～455ms`。Host
`start_vm→vsock ready` P50/P95 从 `1138.668/1149.218ms` 降到
`669.334/678.230ms`；`managed-start` P50/P95 从 `1167.865/1172.404ms` 降到
`694.344/704.743ms`。P95 分别下降 `470.988ms` 和 `467.661ms`，与已定位的约 476ms
RAID6 benchmark 热点一致。

正式 50 次串行验收使用仓库 runner、固定 digest 缓存镜像、`imagePullPolicy: Never`、
worker backend 和 nearest-rank。结果 50/50 成功，manifest name、观察 name、Pod UID 均为
50 个且全部唯一：

| 指标 | S5.5d.2c 旧 Guest | S5.5e.2 新 Guest | 变化 |
|---|---:|---:|---:|
| PodScheduled→Ready P50 | - | 1238.511ms | - |
| PodScheduled→Ready P95 | 1713.888ms | 1252.179ms | -461.709ms（-26.94%） |
| PodScheduled→Ready max | - | 1267.559ms | - |
| RunPodSandbox mean | - | 859.998ms | - |

新 P95 低于本阶段 `≤1.5s` 门禁。W2 保持 cordon 隔离时，runner 现在只容忍
`node.kubernetes.io/unschedulable:NoSchedule`，不需要为测试解除节点隔离。修正前的首轮
Pod 因缺少该 toleration 没有调度、没有产生有效性能样本，已取消和完整清理；正式结果只
来自新的唯一 run ID。

功能回归使用 6 个真实 Cube Pod，全部固定到 W2：

- init/app/sidecar 共用一个 Pod sandbox，disk emptyDir 与 local filesystem PVC 跨容器读写；
- ClusterIP、PodIP、Service FQDN/DNS、ConfigMap 投射均可用；
- `runAsUser=1234`、`runAsGroup=2345`、`fsGroup=2000`、只读 rootfs 与可写 emptyDir 通过；
- `drop ALL + add NET_RAW` 的 `CapEff=0x2000`；另一个
  `allowPrivilegeEscalation=false` 的非 root 容器保持 `CapEff=0`；
- 64Mi memory 与 200m CPU 在 Guest cgroup 中分别为 `67108864`、`20000 100000`；
- privileged Pod 成功创建 `dummy-s55e2`，证明候选内核保留内建 dummy netdev。

W2 CRI 审计确认 6/6 sandbox 的 `runtimeHandler=cube`，6 个独立
`cube-vmm-worker`，多容器 Pod 的 3 个 CRI container（含已退出 init）指向同一 sandbox。
对应 6 份候选 Guest 串口日志仍输出 `using avx512x2 recovery algorithm`，但不存在任何
RAID6 benchmark iteration。清理后 namespace/PV/临时 privileged drop-in/专用目录均移除，
W2 保持 Ready+cordon，Cube sandbox/worker/shim/VM/lifecycle/job/adapter/reaper/share/TAP/
mount/active lease 13 类资源全部为零。
