# S5.5c netlink 网络快路径最终证据

## 结论

S5.5c 的直接范围已经完成，独立 reviewer 已终审 `PASS`（P0/P1/P2=0）：生产默认 backend 已从
`nsenter/ip/tc/ping` 子进程切换为锁定 OS thread 的 netns + netlink，普通启动的网络路径
`network exec=0`；串行/并发 network prepare P95 为 4.313/6.293ms，均低于 25/50ms 门禁。
当前 Cilium IPv4 集群的 DNS、PodIP、ClusterIP、NetworkPolicy、MTU 和真实 W2↔W3 跨节点
Cube Pod 双向访问通过；真实内核 IPv4/IPv6、并发、四类中途故障回滚以及 command backend
回滚也通过，最终资源 exact-zero。

本结论不把累计启动 checkpoint 伪装成通过。`CRI receive→start vm` 的保守上界 P95 仍为
429.479/965.868ms，明确转交 S5.5d.1/d.2；端到端 Ready 也仍未达到 S5.5f 门禁。

## 性能结果

50 串行和 5 轮×10 并发均为 50/50 成功、50/50 唯一关联，固定 digest 且没有 PullImage。
验收统计使用 nearest-rank；单位为毫秒，表中为 P95。控制包 `summary.json` 中 Ready P95
保留了 runner 历史的线性插值输出 1960.992/2683.081ms，不能用于验收；下面 Ready 数字是从
同包原始 `pods.csv` 的第 17 列排序后取第 48 项重新计算。runtime-analysis 中以整数微秒记录的
network/CRI/Shim/worker/Guest 分位数本来就是 nearest-rank，不受此口径修正影响。

尚未达到 S5.5d.2 要求的每轮≤250ms。权威输入是原始 `pods.csv` 与 containerd/runtime
trace 中各 50 个唯一 UID/sandbox，逐 Pod 时间线、summary 和 Prometheus delta 均在控制/W2

Ready 的 nearest-rank P50/P95/P99 分别为：串行
1931.372/1963.978/2002.940ms，并发 2501.209/2691.401/2741.819ms。

串行目录的 `workload-manifests.jsonl` 有 100 行：runner 复用目录时用 append 写入，

正式结果的 `pods.csv`、metrics、containerd trace 和 runtime-analysis 均为 50 个唯一对象。
因此无需重跑，但不能把该 manifest 文件描述成只有 50 条。S5.5d.1 开始前必须让 runner 在
新 run 启动时截断 append-only 输出，并同时断言 manifest、Pod UID、sandbox ID 的期望计数。

## Stage 边界与下一步

S5.5c 只申请对“网络 backend 直接范围”给出 PASS。下列未达指标不是豁免，也不能删除：

- CRI/CNI dispatch、shim resolve/spawn/connect 排队进入 S5.5d.1；先补同钟域偏序时间线，
  再以绝对串行/并发≤80/150ms 为门禁。
- durable create、journal/fsync 和 Host cgroup placement 进入 S5.5d.2；累计 CRI→VMM 仍须
  达到≤220/300ms，absolute VMM start 展开仍须每轮≤250ms。
- Guest cold boot 与常驻内存进入 S5.5e；端到端 1.5/1.8 秒和回归进入 S5.5f。

GLM 的全量 Node E2E 是冻结分支上的外部并行验证，不参与 S5.5c 退出判定；其结果只有在
commit、artifact SHA 和原始结果可复验后才作为后续回归输入。
