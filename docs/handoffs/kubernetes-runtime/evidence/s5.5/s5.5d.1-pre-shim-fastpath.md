# S5.5d.1 CRI/CNI dispatch 与 Shim 连接前快路径

## 结论

状态：`DONE`。修复版 `overlap-v2` 已完成首次正式 50 串行、5×10 并发、功能/故障
回归、双节点 exact-zero 和三份可反向校验证据包。绝对
`CRI receive→Shim create begin` P95 为 75.812/147.511ms，分别满足冻结门禁 ≤80/150ms；
同一 reviewer 终审 `PASS`（P0/P1/P2=0），可以进入 S5.5d.2。

实现 commit 为 `8129b3a9451b21f496f75d3faa8d8ca72ff3b265`，基于 `7a85803e`。
它没有更改“一 Pod 一 Cube VM”、Sandbox/Task
owner、RuntimeClass handler 或 CNI 网络语义，而是把 external shim Sandbox 的内部准备窗口改为
显式并行：containerd 创建 Pod netns 后同时执行 CNI ADD 与 `CreateSandbox`，二者都成功后才允许
`StartSandbox`。

早期 `overlap-v1` 的 CNI/controller duration 结束点晚于真实操作结束，且 Create 后、Start 前的
部分失败点缺少 Sandbox rollback；其结果与证据包全部作废，只保留为调查记录，不构成验收。

## 实现

### containerd v2.3.4 固定版本补丁

- runtime 增加默认关闭的 `sandbox_create_before_network`，且只允许
  `sandboxer = "shim"`；runc 与未开启的 runtime 顺序不变。
- 开启后先 dispatch CNI，再并行调用 external Sandbox Controller `CreateSandbox`；等待两条链
  都成功后继续 `StartSandbox`。
- Create 失败会取消 CNI context 并沿既有清理路径 teardown；由本次取消产生的
  `context.Canceled` 不会掩盖 Create 主因，真实双失败则以 `errors.Join` 保留两条 error chain。
  CNI 失败而 Create 已成功时调用 `ShutdownSandbox`。Create 成功后，从 network metadata
  persist、pause image 检查到 `StartSandbox` 的任一点失败也同步调用 `ShutdownSandbox`；原始
  CRI 失败保持返回主因，rollback 失败记录到既有 `cleanupErr` 并留下可重试清理状态。
- 同一累积补丁保留 `CUBE_PERF_TRACE=1` 的 `CLOCK_MONOTONIC` 埋点；CNI 与 controller duration
  分别在各自回调返回时结束，不包含等待另一条并行链的 join 时间；trace 默认关闭。

配套 Cubelet network backend 在 Pod netns 内等待 CNI 写入接口 MAC/MTU、global IP 和默认路由，
再创建 TAP/tc。netlink 与 command 回滚 backend 使用相同的 2 秒 context-aware wait；command
仅把明确的 device-not-found 视为 pending，权限、缺少二进制、netns 等其他 lookup 错误立即失败。

分析器校验两条独立单调链：

1. `CRI receive→CNI begin→CNI end`；
2. `CRI receive→controller begin→manager→binary→bootstrap→ttrpc→Shim create begin`。

两条链只要求 CNI dispatch 先于 controller begin。controller 链逐段求和必须与绝对 pre-Shim
相等、残差为 0；重叠模式不再重复扣除并发执行的 CNI 时间。冻结绝对门禁始终是权威值。
